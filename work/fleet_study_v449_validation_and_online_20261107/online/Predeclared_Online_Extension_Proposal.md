# Pre-outcome online expansion proposal

Prepared 2026-11-07 before any new online correctness/native outcome. This is a proposed next-stage protocol, not permission to start extra runs, a claim of adequate statistical power, or a completed experiment. All old diagnostic data and failures remain separate.

## Scope and advancement gates

First complete the four archived-state implementation gate and native replay. Advancement depends only on correctness, physical feasibility and process ownership, not on a positive PAIR effect. If any model, controller or gate defect is found, preserve its failure, fix a new source version, repeat the correctness gate, and freeze that version before creating the new cohort. Null/negative diagnostic outcomes are not a reason to replace the seeds or choose easier cases.

The current model is a restricted complete-dispatch experiment: two small delivery vehicles, every old customer, two atomic incoming orders a then b assigned to one common receiver/hub, one supplier truck, and the original customer-flow objective J. It does not optimize all cross-vehicle batch assignments or a sequence of truck destinations. Keep this domain identical across RADIUS, PAIR and the existing Or-opt adaptation.

## Proposed new, fixed cohort

Use the namespace `V449_ONLINE_NEW_01` with exactly eight new mother seeds:

`4499001,4499002,4499003,4499004,4499005,4499006,4499007,4499008`.

For each seed generate one c using the frozen V420 parent generator and one incoming truck origin / first destination using its reveal generator. Set a to that MW/ME destination and b to the other; retain wa=3, wb=4, A/B capacities6/5, service4s, transfer2s, releaseE=6s, both new goods initially aboard the supplier. Customer identities, destinations, old weights, starting stops and initial cargo are held fixed across the following full factorial:

* signal offset0/24;
* slow-background setting0/2;
* pedestrian setting0/10.

This gives 64 related scenarios from eight mothers, not 64 independent orders or seeds. Each traffic-factor comparison is within the same mother with the other two factors fixed. It estimates those specific simulated perturbations, not an effect of generic real congestion. Offsets0/24 both use signals; do not call offset0 a no-signal case. No predictor or arm receives the hidden future pedestrian/background trajectory.

Each scenario needs a new native pre-decision prefix, its observations and sealed hash. A preparer may reuse `research420.history` mechanics, but must write only fresh V449 folders and capture the actual public observations. No model choice, order destination, weight, branch removal, retry selection or stopping count may depend on PAIR−RADIUS outcomes. If feasibility or runtime fails, retain the cell and failure; do not substitute another seed. Deterministic technical retries are allowed only after a documented infrastructure defect and must supersede the entire paired block under an explicit selection record.

## Fixed comparison design

Before new comparative output, freeze all source/network/runtime hashes, cohort JSON and two separate budget modes:

1. Forecast cap: six complete forecasts per receiver/hub branch, at most24 total, including the common four witnesses. This is the continuity comparison with old V420, not equal CPU cost.
2. Wall deadline: one common predeclared deadline measured from before context/setup, greedy, closures and bounds. The current bridge deadline is frozen at 50 milliseconds before diagnostic outcomes. Retain 50 milliseconds for continuity in the proposed new cohort; any additional budget needs an explicit pre-outcome amendment. The old code had a post-hoc <1-second assertion, which is not an equivalent interrupting budget. Use only improvements timestamped by the deadline. Late final plans/proofs remain secondary records.

Use three timing repetitions per scenario/arm, rotating arm order deterministically. These repetitions estimate measurement noise and do not increase n. All policy timing finishes before native replay. For each scenario and budget, replay every distinct selected plan once under the same prefix and SUMO random seed. Reusing an identical plan's deterministic replay is allowed only with exact plan/prefix/source identities; map all arm/repetition selections to that artifact. Repeated identical native runs are not new independent traffic observations.

RADIUS versus PAIR is the pure information/check ablation: same common priority, seeds, candidates, exact forecast, continuations and budgets. Report additional checks and actual extra cuts as well as expanded states, full forecasts, elapsed time and literal-budget J. Or-opt is the frozen published-method adaptation with a different candidate-exploration policy; it is an external algorithm comparison, not an attribution of a difference solely to the capacity bound. If a lazy/eager policy ablation is later added, preregister it as a separate factor and do not relabel it as the same two-arm test.

## Outcomes and aggregation

Primary bridge outcome is actual SUMO customer-flow J for a plan available within its assigned budget. Retain predicted J, actual J, forecast error, first/last handoff, truck dwell/departure, individual old/new completions and all completion/physical audit failures separately. Last handoff, truck departure and last customer delivery are different timestamps. Lower predicted J is not automatically better actual traffic service; count direction reversals and unchanged plans explicitly.

For timing report all cases' deadline-quality coverage and misses first; any completion-time ratio must use the identical eligible paired subset with its denominator. Do not pool successful complete runs with censored or late ones. Report all64 cells, mother-level paired summaries, each traffic stratum, wins/ties/losses, worse examples and null cases. Use seed/mother as the independent resampling unit if uncertainty intervals are later requested. Eight mothers support a bounded development/validation study, not a broad deployment claim.

Freeze a source-bound full permutation oracle on the original small domain before new outcomes if exact forecast-optimality gaps are needed; run it outside policy timing and never feed its optimum or plan to a policy. Native SUMO is a physical execution check for the fixed synthetic network, not an exact optimizer or a calibrated digital twin. Public-road calibration/validation elsewhere cannot transfer its numerical accuracy automatically to this delivery network.
